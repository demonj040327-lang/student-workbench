## 2. Campus Skill Exchange：可以嫁接，但不整体搬迁

### 源码发现

- `server/src/services/matchingEngine.js` 使用教/学技能标签的精确包含关系打分，并非大模型语义匹配。
- 原评分中的 `learnMatch` 与 `mutualInterestBoost` 实际重复计算同一方向的交集；前端把原始分数展示成百分比，不具有概率或能力评估意义。
- `server/src/controllers/sessionController.js` 的更新函数检查状态名称，但没有充分约束操作者是否为参与者、是否有权接受邀请，以及状态转换是否合法。存在登录中间件并不等于会话对象已做好授权。
- 其账号、MongoDB、评分、信誉分和管理后台与当前平台的数据结构不同，直接整站合并代价高。

### 当前整合

新增学生导航“同伴互助”，保留现有浅色界面和双语切换。

1. 学生选择自己愿意讲解和希望学习的课程，可跨课程保存需求；不要求选到知识点，具体问题由双方讨论。
2. 匹配只要求教与学需求对应同一门课程，并有相容的交流语言、相同的意向时段；排序奖励双向互助，不展示能力分或匹配百分比。
3. 推荐卡片列出“对方可以帮你”和“你可以帮对方”的课程。
4. 学生发送邀请；仅接收方可以接受或拒绝，仅发起方可以撤回待确认邀请。
5. 接受后可文字交流，任一参与者可以结束；结束后记录只读。
6. 会话只向双方提供，服务端校验权限、状态、重复邀请及输入长度。
7. 采用原项目的功能思路重新实现，没有引入 MongoDB、Express、默认管理员或原信誉分机制。许可和贡献边界见 `THIRD_PARTY_NOTICES.md`。

### 演示方式

- 打开学生端 → 同伴互助 → 选择课程 → “载入本课程演示搭档”。
- 系统创建明确标注的演示同学 A/B/C；A 有学习需求，B 能提供讲解，并有反向需求。
- A 发送邀请；切换为 B 接受；双方打开交流窗口发送消息；最后结束互助。
- 只有演示区允许切换这些固定身份。普通工作区没有虚构学生，也不允许通过接口切换为其他参与者。

### 数据与边界

- 新接口：`/api/peer-learning`；记录存于被 Git 忽略的 `data/peer-learning/demo.json` 和 `workspace.json`。
- 使用 HttpOnly 浏览器身份 cookie，由服务器分配身份，普通工作区不能在请求体中指定自己是谁。不同浏览器在同一本机服务上可以保存独立资料并交换邀请/消息。
- 这是本机原型，不是学校账号验证；清除 cookie 会失去原浏览器身份，显示名称不代表真实学籍。
- 服务仍限制回环地址。尚不能让外部同学直接通过互联网访问；未接入学校 SSO、正式课程成员权限和跨设备账户恢复。
- 目前只有课程的规则匹配，没有自然语言语义匹配、视频、AI 主持或自动学习能力评分。
- 可用时段是意向分类，不是精确预约；选择“愿意讲解”仅为学生自我声明。
- 文字交流以约 5 秒轮询刷新，不是 WebSocket；最多 200 条消息/会话，单条最多 2,000 字符。
- 讨论引导为固定模板，明确标注，不冒充 AI 内容或教师作业。

## 3. OpenMAIC：借鉴生成控制，不引入大批课堂内容

其课程生成结构支持 slide、quiz、interactive、PBL；生成内容与播放/互动动作分开。`lib/classroom/generation-permission.ts` 将生成权限作为统一前置条件；`lib/constants/generation.ts` 明确限制资料字数、图像数量与大小。

针对本平台的取舍：

| 能借鉴的机制 | 对本平台的意义 | 当前决定 |
| --- | --- | --- |
| 明确的生成类型与结构 | 讲解和题目独立生成，不因上传就生成整套课堂 | 保留并强化现有“草稿/题目”分离；不接入全套课堂 |
| 统一生成权限 | 避免学生预览或重试使用教师额度 | 沿用本项目已有教师/学生 API 隔离；未来再审查统一权限入口 |
| 内容量与媒体限制 | 控制长课件成本、时延与输出规模 | 建议进一步提供生成范围选择与预算显示，尚未新增 |
| 持久化运行和恢复 | 页面关闭后能继续后台生成 | 有价值，但需要服务端任务持久化；本次不迁移其 Postgres/运行时 |

不在此次匹配功能中导入 AI 老师、AI 同学、视频、互动场景或 PBL。避免内容泛化和依赖膨胀。主项目 MIT，内置第三方包仍有独立许可；本次只作架构参考。

## 4. DeepTutor 与当前平台对比

| 维度 | 当前 Student Workbench | DeepTutor 源码中可见的做法 | 提升建议 |
| --- | --- | --- | --- |
| 上下文连续性 | 阅读时跟随当前页；请求主要包含当前问题和相关课件文字；聊天显示在组件内 | 多种能力有共享会话上下文，mastery 历史状态进行有界处理 | 优先：保留同份课件的有限会话历史、换资料时隔离，仍要求出处 |
| 提问引导 | 以源文件前几页标题作为快捷提问 | `mastery_hints.py` 根据知识点与最近对话生成简短提示，并缓存/限时 | 优先：基于当前页或当前主题建议问题，避免每次打开重复调用 |
| 学习路径 | 3–5 模块、阅读步骤、选择题与手动完成记录 | 有独立 mastery path、course study、immersive reading 等能力 | 暂不迁移：先保持课程要求清晰，避免引入另一套平台结构 |
| 视觉理解 | PDF 页面可视，但问答主要读取提取文字，图片页可能无可用文字 | README 与能力层提供可视化及原始来源视觉练习等功能 | 后续：按需只发送当前页图像，须验证学校 ELM 的视觉模型和资料授权 |
| 题目格式稳定性 | 已要求四个文字选项、0–3 答案和有效来源页；之前遇到过模型格式不一致 | `capabilities/mastery/choices.py` 将标签、文字内容与答案规范化分开处理 | 建议把模型输出规范化与业务校验进一步分层，保留本项目严格的四选一和来源要求 |
| 长任务恢复 | 前端队列允许切页，但刷新/关闭会中断 | 服务端会话、存储和恢复机制更完整 | 后续：将现有任务移入服务端持久化队列，不整体搬它的后端 |
| 学校工作流 | 已有教师草稿、发布/撤回、周次、Coursework、个人时间轴 | 更侧重个人学习工作区与能力系统 | 保留本项目学校场景的优势，不以换皮替换现有教师流程 |

最值得下一步做的两项是“当前课件内的连续问答”和“当前页相关的提问建议”。它们是评审建议，本次没有擅自接入 DeepTutor 或额外调用模型。

## 5. 验证与第三方署名

- `server/peer-learning.test.mjs` 检查课程隔离、语言/时段、双向匹配、重复邀请、参与者权限、合法状态转换、消息只读、浏览器身份隔离、跨站拒绝和演示/普通数据隔离。
- 浏览器验证覆盖完整邀请/接受/交流/结束流程、刷新后记录、双语与手机布局。
- 完整构建使用 `npm run build`。
- 第三方代码评审不代表对其所有功能或安全性背书；本项目新增功能的验证范围单独记录。
