## 先统一的对象与接口

共同确认 Course、Material、Coursework、StudentProgress。作业状态 draft/published，发布时间 releaseAt、截止时间 dueAt、时区 timezone 均显式保存；学生步骤完成和 submitted 分开。教师改期追加 revisions，不重置现有步骤进度。课件与作业说明分两条流程。

当前接口：POST /api/study/parse、/coursework（字段+原文证据）、/plan（带引用步骤）、/generate（课件指导与练习）、/ask（当前资料问答）。成员 B 和 C 先冻结请求/响应格式，前端再并行对接。

## 建议执行顺序

1. 首次会议：确认五人负责人、课程对象、数据结构、接口与演示路径；先选一份课件和一份作业说明作为共同测试资料。
2. 第一阶段：每人完成最小闭环。前端允许使用明确标注的测试数据；AI 先把原文提取与引用校验做稳；账号成员先提供最小师生身份与课程归属。
3. 第二阶段：接真实接口和统一存储，验证跨角色发布、个人进度隔离、定时发布、改期提醒及提交记录。成员 C 的账号接口未就绪时，明确保留本地演示边界。
4. 第三阶段：完成手机和电脑回归、教师内容核对、可用性试用与演示视频。以官方截止时间倒排内部冻结时间，至少留一个完整联调周期。

## 协作规则

- 每人使用独立功能分支，通过小型 PR 合并；尽量避免两人同时修改 CampusApp.tsx 或同一段样式。
- 将 CourseworkEditor 和学生页面逐步拆成独立组件，配色集中复用；新功能不自行更换视觉方向。
- 每个任务必须写清输入、输出、负责人、验收场景和完成日期。每天简短同步阻塞问题。
- 先完成一门课的教师发布到学生学习全流程，再扩大课程数量；录音、视频生成、原生 App 打包暂不挤占核心开发。
- 最终汇报必须区分已经实测、演示数据和计划能力，不把本地视角切换当成学校身份认证。
