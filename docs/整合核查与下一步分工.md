# workbench 整合核查与下一步分工

核查日期：2026-10-24。核查对象：本地 `feat/peer-learning` 分支及当前应用入口 `RoleGate → CampusApp`。本文依据保存的代码、精选资料的解析结果和本轮回归检查，不把旧版组件存在视为已经接入当前产品。

## 1. 当前判断

项目已经具备“教师发布资料 → 学生按周阅读与练习 → 个人问答 → 作业推进 → 同伴交流”的本机原型。接下来最有价值的工作是统一多人数据、提高 AI 学习流程可靠性、补齐可安装与交付方式；不建议继续堆叠新的 AI 页面。

本分支的学习搭档已改为按课程选择愿意讲解和希望学习的内容，不要求选择知识点。语言和意向时段继续作为筛选条件；具体问题由双方在聊天中确认。同课程下的旧知识点选择会合并，历史邀请和消息保留。课程不要求已经上传课件才能参与匹配。匹配是规则匹配，不是 AI 对学生能力的判断。

## 3. 整合后优先优化

### P0：把不同模块连接成同一套数据

目前课程和进度使用 localStorage，课件使用 IndexedDB，讨论与反馈使用另一套 localStorage，学习搭档使用服务端 JSON，而 SQLite 课程接口另有一套对象和 `teacher-demo` 身份。用户界面连起来了，但数据和身份没有统一。

先定义用户、课程成员、资料版本、作业、个人步骤、学习活动、讨论和互助会话的共同标识。由服务端判断教师和学生权限；不要通过 URL 的 `role` 或前端课程筛选承担真实鉴权。先打通两个浏览器、一个教师与两个学生的闭环，再考虑学校 SSO。

### P0：固定一条不会中断的演示路径

主线用 HCI 第 5 周；其余学科作为补充。录制前确认个人 API、原文可加载、题目有出处、作业已审核发布、浏览器地址一致。真实作业的日期没有核实前保留草稿，学生端看不到是发布状态控制，不是导入失败。

示例进度、班级统计和演示搭档若为虚构内容应明确标注；不要把本机记录说成真实教学成效。

### P1：提高学习内容的连续性

增加按资料保存的问答会话，允许追问“为什么”“再举例”，把必要历史传给模型并控制上下文长度。然后扩展到同课程多文件检索，仍保留文件名、页码、当前页范围和跨课程隔离。

课件篇幅较长时，可先生成 3–5 个顶层模块，再在模块内展开子节，避免把完整文档直接变成十几个平级关卡。错题复习优先使用已有练习记录，不必再增加独立产品。

### P1：后台任务与使用体验

生成任务需要从网页内存迁到可恢复的服务端任务，最少有任务 ID、状态、错误与结果；刷新后能继续查看，重试不能产生重复草稿。当前页面可以边生成边操作，但还不等于持久后台任务。

先做稳定的加载、空态、错误恢复和键盘可用性，再增加动效。阅读页可固定返回与页码工具栏，长页阅读时仍能返回；把“当前资料”和使用提示折叠，给对话与原文留出更多空间。保持原有浅色视觉。当前多份旧样式和旧页面仍在仓库，后续可拆分 `CampusApp.tsx` 并收敛样式，但不要在录屏前进行大范围重写。

### P1：可安装与交付

使用 PWA 作为手机可安装、电脑可访问的第一步。安装缓存应限于应用外壳；私人资料、聊天和 API 请求不能被无差别缓存。学校资料与 Key 不加入公开构建产物。公网演示必须部署后端，不能只上传 `dist`。
